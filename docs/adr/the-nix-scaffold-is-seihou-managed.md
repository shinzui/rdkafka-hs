# The Nix scaffold is seihou-managed

## Context

The repository's flake comes from the seihou module `nix-haskell-flake`
(`mori://shinzui/seihou-modules`, project path
`modules/haskell/nix-haskell-flake/`; artifact URI pending), which pins the shared
GHC toolchain and nixpkgs and generates `flake.nix`, `flake.lock`, `nix/haskell.nix`,
`nix/treefmt.nix`, `nix/pre-commit.nix`, `nix/redpanda.nix`, `fourmolu.yaml`,
`process-compose.yaml` and the ignored `.envrc`. While bootstrapping, three
surprises showed how easily the managed and project-owned parts get mixed: the
generated `nix/haskell.nix` is not `nixpkgs-fmt` clean, so the pre-commit formatter
rewrote a managed file; reconfiguring with one `--var` reset an earlier override
(`nix.kafka`) to its default; and `rdkafka.pc`'s private requirements were missing
from the dev shell.

## Decision

Managed files are never edited by hand, and the formatter does not touch them:
the unmanaged `flake.module.nix` excludes `flake.nix` and `nix/*.nix` from treefmt.
All project wiring lives in `flake.module.nix` (c2hs, the pkg-config inputs of
librdkafka's private dependencies, the `RDKAFKA_TEST_BROKER` shell variable) and in
`process-compose.override.yaml` (the private broker process).

Reconfiguring passes every non-default variable explicitly:

```bash
seihou run nix-haskell-flake --var nix.kafka=true --var nix.redpanda=true
```

The broker ports are seihou variables (`redpanda.*-port` in
`.seihou/manifest.json`); changing one means rerunning seihou and updating
`flake.module.nix`, `test-integration/Kafka/TestEnv.hs` and `README.md`.

## Consequences

Toolchain upgrades arrive by releasing a new `nix-haskell-flake` version and running
`seihou update`, not by editing pins here. `git diff` after a reconfiguration
should show only managed files and `.seihou/` changes; anything else is a sign that
project wiring leaked into a managed file.
